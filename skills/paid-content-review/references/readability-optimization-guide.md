# 课程可理解性优化指南

用于课程、专栏、教程和知识星球正课的“难懂句子检查、术语优化、表达优化、跨章叫法统一”。目标不是把作者风格磨平，而是消除读者必须停下来猜意思的地方。

## 一、审查边界

优先处理以下问题：

1. 抽象词代替了具体动作或结果；
2. 作者内部术语未解释，普通读者不知道要做什么；
3. 同一概念在不同章节使用不同名称；
4. 两个不同流程用了相似名称，读者会误以为是同一件事；
5. 产品界面名称直接出现，但没有说明选项的作用；
6. 指代、数量、前后引用或活动入口不完整；
7. 句子简化后丢失事实核对、适用范围或人工判断等必要边界；
8. 错字、标点、大小写和 Markdown 格式影响阅读。

不要自动处理以下内容：

- 已在附近清楚定义的必要专业词；
- 产品界面、功能或按钮的官方名称；
- 读者能直接理解、且承载作者语气的比喻；
- 只是不符合审查者个人文风，但不影响理解的句子；
- 用户明确否决的修改建议。

## 二、判断标准：读者是否需要猜

逐句问五个问题：

1. 读者能否指出这句话要求谁做什么？
2. 读者能否知道做完会得到什么？
3. 术语第一次出现时，附近是否有人话解释或例子？
4. 换到另一章，同一概念是否仍使用同一名称？
5. 删除上下文后，这句话是否仍可能被理解成另一件事？

命中任意一项时记录候选问题，但不要立即改稿。先结合前后文确认它是真问题，而不是有意留白或修辞。

## 三、七类高频问题与改法

### 1. 抽象结果改成可观察结果

失败信号：出现“发生、出现、沉淀、赋能、形成资产、进入循环”等词，却没有说明留下了什么。

改写方法：写出具体产物、动作和后续用途。

```text
抽象：让真实材料出现，让真实表达发生。
具体：留下一段真实素材，完成一次真实表达，并让它成为下一次创作的素材。
```

### 2. 概括动作改成动作清单

失败信号：使用“聚合几个动作、完成中间流程、推进内容”等表达。

改写方法：直接列出读者会经历的关键动作。

```text
抽象：把几个动作聚合到同一段会话。
具体：在同一段会话里完成素材整理、内容洞察、角度选择和口播初稿。
```

### 3. 保留官方名称，同时解释作用

产品选项、按钮和功能名不能擅自改名。第一次出现时采用“官方名称 + 人话解释 + 无此选项时的替代动作”。

```text
选择“仅限项目”的记忆，让 AI 只参考这个项目里的内容；如果没有这个选项，就在输入末尾明确要求只根据本次材料判断。
```

### 4. 避免流程名称碰撞

同一课程中，“短路径、快速通道、简化流程”等近义词容易被误认为同一流程。

- 确实是同一流程：统一名称；
- 只是省略了其中一个动作：不要借用正式流程名，直接描述省略了什么。

```text
易混：这个案例走的是短路径。
清楚：这个案例没有继续追问，而是直接进入了洞察卡整理。
```

### 5. 内部术语改成读者语言

优先替换下列类型的内部术语：

| 内部术语 | 更清楚的表达 |
|---|---|
| 内容母稿 | 不针对具体平台、便于继续改编的基础稿 |
| 下一集钩子 | 下一篇可以继续回答的问题 |
| 互动钩子 | 引导读者回应的问题 |
| 理解脚手架 | 帮助理解的提示材料 |
| 一句话抓手 | 一句话总结 |
| 分块消化卡 | 分段理解卡 |
| 做小迁移 / 检查迁移 | 换一个场景仍能解释或使用 |

替换后必须横向搜索全目录，避免标题、表格、项目指令、案例正文和图片 `alt` 使用不同名称。

### 6. 看不见的过程改成可检查过程

失败信号：使用“后台完成、自动继承、完整复刻”等技术感表达，但实际只是 AI 在一次回复中连续处理。

```text
含糊：项目会在后台完成中间动作。
清楚：AI 会在同一次回复里完成洞察提炼、角度选择和口播初稿，你仍然可以逐项检查。
```

简化时不得删除人的责任。涉及事实、观点、公开边界和风险判断时，必须明确由谁确认。

### 7. 引用与数量必须可回查

重点检查：

- 文中写“六项”，清单实际是否六项；
- “按活动说明”是否给出真实链接或位置；
- “上一讲、下一步、前四讲”是否对应当前顺序；
- 产品名称和大小写是否统一；
- 表格、正文、提示词中的输出名称是否一致。

找不到引用目标时，补链接或直接写出动作；不要保留悬空指代。

## 四、全目录审查流程

1. 明确目标读者和当前阶段；可理解性专项不强制询问定价。
2. 列出用户指定范围内的全部正文文件和行数。
3. 按学习顺序全量通读，理解每章承担的任务和术语定义位置。
4. 记录候选句，标注文件、行号、问题类型和修改理由。
5. 用 `rg` 扫描术语、近义叫法、产品名称、数量词、旧表达和明显错字。
6. 合并重复问题，避免同一个术语逐条报十次；指出首次定义处和全部受影响位置。
7. 先给修改方案，不直接改文件。
8. 用户批准部分建议后，只修改批准清单；不顺手改其余候选项。
9. 修改后重新搜索旧表达，并用差异检查确认没有扩大修改范围。

## 五、优先级

- **P0 必改**：措辞会直接导致错误操作、错误数量、错误入口，或删掉必要的安全边界。
- **P1 建议改**：读者需要停下来猜术语、流程或动作；跨章名称冲突；一句话可能被理解成不同流程。
- **P2 可优化**：错字、标点、大小写、格式和不影响核心理解的轻微冗余。

不要为了凑数量把作者风格、普通比喻或已定义术语都列为问题。

## 六、报告结构

```markdown
# 可理解性审查

> 范围：<文件数 / 章节数>｜读者：<目标读者>｜阶段：<只给方案 / 改稿期>

## 总体判断
- 最容易卡住的三类表达：
- 建议优先修改的数量：

## P1 建议优先修改
| 位置 | 当前表达 | 为什么难懂 | 建议改为 |
|---|---|---|---|

## P2 顺手清理
| 位置 | 问题 | 建议 |
|---|---|---|

## 不建议修改
- <保留作者风格或必要术语的说明>
```

## 七、批准后修改与验收

用户明确允许修改后：

1. 把批准清单逐项映射到文件和当前文本；
2. 当前文本与报告不一致时，以当前文件为准，不做模糊批量替换；
3. 修改提示词中的术语时，同步修改正文说明、表格、案例和图片 `alt`；
4. 保留官方界面名称，并在首次出现处补解释；
5. 不修改用户未批准或已经否决的建议；
6. 运行旧词扫描和 `git diff --check`；
7. 回读修改后的完整段落，确认句子更清楚且没有削弱原意和边界。

最终回执要说明：修改了哪些文件、哪些术语已统一、哪些建议按用户要求未改，以及完成了什么验证。
