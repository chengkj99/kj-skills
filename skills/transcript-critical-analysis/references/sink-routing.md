# 沉淀落位

用户明确要求沉淀时才写文件。只要求分析时，把结果留在对话里并说明建议去向。

## 先读目标仓库规则

不同仓库的目录职责和授权边界差别很大，**先读 `AGENTS.md`、`CLAUDE.md` 或仓库内的 README 约定，再决定落点**。用户本次指定的路径优先于本文件的任何默认建议。

需要特别确认三件事：

1. 哪些目录是「原始证据」区，禁止被整理稿覆盖或修改。
2. 哪些文件是生成产物或只追加日志，不能手工改写。
3. 沉淀后是否需要运行索引/台账刷新脚本。

## 四类产物的落点

| 产物 | 性质 | 落点原则 |
|---|---|---|
| 原文 / 轻度整理稿 | 保真证据 | 事件或素材归档区，原文与整理稿分文件 |
| 按论证重排的可读稿 | 结构化实录 | 个人阅读用途放个人记录区；要进知识库的放结构化实录区 |
| 我的评估与压力测试结论 | 解释性产出 | 深度解析区，或经确认的结论纪要区 |
| 自检问题与待验清单 | 行动 | 随可读稿附录，或个人待办/笔记区 |

三条硬约束：

- **原文与整理稿分文件**，任何情况下不合并。
- **讲者原意与我的评估分页面或分版式**，不要在同一段里交替出现。
- **可复用方法只在用户明确要求形成 SOP / Playbook 时才写成方法文档。** 分析一份材料的副产品不等于一份通用方法。

## 元数据建议

归档原文时记录来源与状态，便于日后回查和判断可用性：

```yaml
---
title: "事件标题（原始文字稿）"
date: YYYY-MM-DD
archived_at: YYYY-MM-DD
source_path: "用户提供的路径或附件标识"
privacy: private
fidelity: original-transcript
---
```

整理稿额外链回原文，并把保真级别降一档（例如 `fidelity: lightly-edited-transcript`、`source_file: <原文文件名>`）。

分析报告建议记录：材料来源、分析日期、置信度总体说明（尤其是「本次未联网核实」这类限制）、以及哪些结论属于我的推断。

## 完成后的登记

按目标仓库规则执行，通常包括：

1. 更新对应索引或目录页。
2. 在只追加日志文件末尾追加本次记录，不修改历史行。
3. 运行仓库提供的台账 / Dashboard 刷新脚本。

日志里如实写清：创建了什么、更新了什么、跳过了什么、以及未执行的事项（比如未核实、未提交、未推送）。

## 不要做的事

- 不因为「看起来有价值」就把个人记录区的内容自动知识化。
- 不在未获明确要求时提交、推送、部署或发布。
- 不把分析结论写回原始证据文件。
- 不把私密材料的细节带进任何公开产物；公开引用时只用脱敏占位。
